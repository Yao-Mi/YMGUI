# 视频回流的效率验证

从仓库根目录运行 `./tools/benchmark_video.sh`。脚本构建 Release/PIC 双色深核心，在 Linux PC 上运行像素/传输一致性检查和以下测量，日志位于 `build/logs/video-benchmark/results.log`。不自动设置性能通过阈值；计时受CPU负载影响，不能代替目标板测试。

- `black_fill`：全部透明度的像素对照；用 `YMGUI_BlackLutEnabled` 比较查表与此前的标量优化路径。301次交替顺序测量，恢复背景在计时外，报告中位耗时；分别测多色和纯色、整帧/条带/小块。RGB565均匀采样保留原重复像素缓存，避免纯色退化。
- `staged_flush`：320×240帧，320×48中转缓冲；比较拒绝/允许直发时的像素、回调次数、中转字节和平均耗时。send模拟为内存复制，不代表物理DMA/面板耗时；回调返回时传输已完成。
- `image_content`：320×480 Image显示320×240 FIT内容，301次更新逐像素比较；统计整控件/内容区域失效的刷新量及平均耗时。UI初始化、布局变化仍完整失效，此例50%的流量收益随实际黑边比例改变。
- `video_buffers`：使用播放器的原始帧管道测试夹具，统计帧分配/引擎整帧拷贝/seek分配；验证部分读取、完整帧发布、队列回绕、未完成尾帧与消费交错、未来帧保留、稳定显示地址和EOF。seek的进程启动使用空文件夹具；实际FFmpeg路径由播放器有限帧自检验证。

要复验旧播放器，可先提取改动前的 `vp_video.c` 到临时文件，再设置 `BENCHMARK_PIPELINE_SOURCE=/absolute/path/vp_video.c ./tools/benchmark_video.sh`。这只更换帧缓冲测量的实现，不修改源码。其余三项仍测当前核心的对照路径。

## 本轮测量结果（2026-10-08）

Linux x86_64、GCC 11.4，核心 Release/PIC，测量代码 -O3；时间单位 µs。以下是本次运行结果，重新运行不要求相同时间。

| 步骤与样例 | RGB565：原路径 → 新路径 | RGB888：原路径 → 新路径 | 确定性收益 |
| --- | --- | --- | --- |
| 黑色遮罩，多色320×240 | 503.258 → 192.204（2.62倍） | 292.360 → 116.426（2.51倍） | 任意透明度像素相同 |
| 黑色遮罩，纯色320×240 | 87.212 → 87.259（持平） | 253.354 → 99.113（2.56倍） | RGB565保留重复像素缓存 |
| 同步中转 → 可访问源直发 | 24.851 → 10.452 | 40.958 → 23.010 | 中转153600/230400字节 → 0；5次发送 → 1次 |
| FIT整控件 → 内容失效 | 63.649 → 32.430 | 343.729 → 131.020 | 153600 → 76800刷新像素；301帧相同 |
| 播放器320×240帧池 | 2150400 → 1996800字节 | 3225600 → 2995200字节 | 14 → 13帧；引擎整帧复制2 → 1次；seek帧分配12 → 0次 |

黑色查表最初使RGB565纯色大区域退化约两倍，补充均匀采样后消除了该退化。256像素以下不建立表；RGB565纯色16×16本轮0.351→0.360 µs，存在约9 ns判断开销，不能宣称每种输入都加速。未测物理LCD/DMA，也未把主机收益换算成硬件帧率。旧播放器使用改动前源码夹具复测内存、拷贝和seek分配；原移植工程未修改。
